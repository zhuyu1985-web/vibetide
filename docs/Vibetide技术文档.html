07 · 四层模型

数字员工四层模型

系统把「数字员工」拆成四层正交概念：工具 → 技能 → 工种 → 场景。员工是「工种」的配置实例、连接四层的枢纽。这套模型对标真实媒体团队，让能力跨「中心 / 领域 / 媒体形态」复用（最新一次重构 commit a80339a「工具 / 技能 / 工种 / 场景应用」）。

实线（绿）：派单 / 绑定 实线（青）：实例化 / 运行时调用 虚线：工种定义核心技能

四层自上而下：场景编排技能步骤 → 按所需技能派单到对应工种的员工实例 → 员工绑定技能 → 技能运行时调用工具。员工是「工种模板」的配置实例，是连接四层的枢纽。

四层逐层定义

① 工具 TOOL

通用能力，不归属工种

数据获取 / 检索 / 可复算分析（读）与状态变更（写）。所有非 observer 员工无条件注入读工具；写工具受 authority 门控。单一真相源 tool-kinds.ts、skills.kind='tool'。判定准则：换个工种来用、逻辑与产物一样 → 工具。

② 技能 SKILL

工种强相关的专业能力

必须经 employee_skills 绑定到工种才能调用（硬边界）。SkillOwnership{core, shared[]} 声明归属、compatibleRoles 限定可用工种。判定准则：代表某工种专业判断、换人变味 → 技能。

③ 工种 CRAFT（＋员工实例）

对标媒体岗位的能力模板

10 个工种（编导 / 记者 / 编辑 / 评论员 / 后期 / 审核 / 运营 / 播报 / 分析 / 制片）。员工＝工种 ＋ 领域标签 ＋ 额外技能 ＋ 权限 ＋ 平台规格 的实例，承载于 ai_employees.roleType ＋ instanceConfig。

④ 场景 SCENARIO

工作流编排的技能步骤

workflow_templates 是所有「场景」单一真相源（每 org 27+ 内置、12 category）。每步声明 requiredSkill，启动时按 requiredSkill → compatibleRolesFor → pickEmployeeForStep 确定性派单到员工。

工种从哪来：对标真实媒体台的岗位收敛

这 10 个工种不是拍脑袋定的，而是对标真实媒体台的岗位结构收敛而来。以北京广播电视台为例（9 个频道中心 ＋ 5 个广播中心 ＋ 融媒体平台 ＋ 16 个职能部室），关键观察是：每个内容中心（新闻 / 文艺 / 财经 / 体育…）的岗位几乎是同一套，变的只是领域——体育记者 ≠ 新闻记者，不是工种不同，是领域不同。于是「中心」不必做成系统实体，用「绑不同知识库 / 项目上下文」表达即可；真正跨中心复用的，是那套岗位 = 工种。

三维如何修饰：改什么 · 怎么落地 · 差异在哪

三个维度正交——各自作用在 agent 的不同部位、互不干扰，所以少量工种 × 配置就能组合出大量岗位：

维度改变 agent 的什么怎么落地（字段 / 机制）同一工种的差异化举例
领域 domain 知识来源 ＋ 视角 / 术语 绑 employee_knowledge_bases（主，限定 kb_search 检索范围）＋ instanceConfig.domainTags（补，注入 prompt 领域标签） 记者绑《财经库》→ kb_search 查财报、谈股价 / 营收；绑《体育库》→ 查赛事、谈积分 / 战术——同一条素材落点完全不同

三维组合出实例：同一个「记者」工种可配出——① 《财经库》＋ advisor ＋ news ＝ 财经记者（出规范财经稿、交审）；② 《科技库》＋ advisor ＋ newmedia ＝ 科技新媒体记者（出口语化科技短文案 ＋ 话题标签）；③ 同记者升 executor ＝ 有定稿权的资深记者。维度正交、互不干扰，这就是「8~10 工种覆盖几十岗位」的数学来源。

ℹ 一句话记住三维落点

领域改「知道什么、用什么视角」（知识库 ＋ domainTags）；层级改「能拍板到哪一步」（authority → 工具集 ＋ 产出状态）；形态改「产物长什么样、给哪个平台」（mediaForm ＋ platformSpecs → prompt）。三者分别落在知识层 / 权限层 / 输出层，零耦合。

实战：给员工配了领域 / 形态后，运行时到底发生了什么

以「让财经记者做线索采集」为例，追一遍从配置到执行——重点是领域 / 形态走两条完全不同的路：roleType 参与派单选人，而 domainTags / mediaForm 只进 prompt。

绿路：roleType → 派单选人 蓝路：领域 / 形态 / 知识库 → 只进 prompt

同一份配置分两路：工种（roleType）决定「派给谁」，领域 / 形态 / 知识库决定「选中的人怎么干、产物什么味」。两路互不交叉——这是下面那个「坑」的根因。

配了 domainTags=["财经"] ＋ mediaForm="news" 后，assembleAgent 给 system prompt 实际多注入这两段（原文）：

# 领域专精（Layer 4.5 · 因 domainTags=["财经"]）

- 使用该领域的专业术语与表达习惯，不说外行话。

⚠ 关键坑：领域 / 形态只改「产物」，不改「派单选人」

pickEmployeeForStep（mission-core.ts:135）派单时只看 roleType（工种）＋ isPreset，完全不看 domainTags。所以若你有多个 reporter 实例（财经记者、体育记者…），笼统说「让记者采集」可能派到非财经那个，再靠 prompt 补领域口径——往往不是你要的。要精确派给财经记者，必须在场景步骤里显式指定该员工实例（employeeSlug），或让该领域只配这一个 reporter 实例。

所以「让财经记者做线索采集」的正确操作：

  1. 配实例：/employee/[id] →「领域·形态」Tab 设 domainTags=["财经"]、mediaForm="news"，「知识库」Tab 绑《财经知识库》→ 保存（走 updateEmployeeInstanceConfig 写 instanceConfig）。
  2. 选对技能：系统没有独立的「线索采集」skill——记者用核心技能 content_generate ＋ 通用检索工具（web_search / trending_topics / news_aggregation / web_deep_read）组合完成采集。
  3. 确保派对人：因 domainTags 不参与派单，在场景步骤里显式指定这个财经记者实例（employeeSlug）。它被选中后，prompt 已带财经口径 ＋ 财经库 kb_search，产出就是「财经味」的线索采集结果。

⚠ 熟练度（proficiencyLevel）是「软提示」，几乎没有硬作用

它由 avg(employee_skills.level) 算出（默认 50），但全库唯一消费点就是上表第 2 段——按 ≤30 / ≤70 / >70 拼一句「严格按步 / 适度发挥 / 自由创新」的文字。它不影响模型选择、不影响 temperature、不过滤工具、不改 stepCountIs(20)、不进任何 if 分支。换句话说「说说而已，LLM 自己看着办」。真正硬性改变执行的是权限（决定工具集）、技能执行指南（决定流程）、真实性约束这几段。认知引擎（cognitive/skill-manager.ts）会按任务质量动态调 level，但调完也只是换那句提示的档位——所以「感觉它没什么作用」是准确的。

执行 executeAgent()

  • 执行期才构建真实工具：createKnowledgeBaseTools + toVercelTools(...)，每个工具用 wrapToolExecuteWithContext 注入 org/operator/mission/task 上下文。
  • 注入时间基准：把「当前日期」写进 prompt，防 LLM 按训练截止日误判时效、给搜索设错时间窗。
  • skillSpec 硬约束：步骤绑定 SKILL.md 时，整篇 body pin 进 system prompt，强制三段式输出（执行摘要 / 执行过程 / 产出结果，各 ≥100 字）。
  • 调用：generateText({ stopWhen: stepCountIs(20), maxOutputTokens, abortSignal: AbortSignal.timeout(3min) })。
  • 失败检测：onStepFinish 扫 toolResults（AI SDK v6 用 .output 非 .result）收集 success:false，有失败则 override status="failed"（优先级高于 needs_approval）。

ℹ 多智能体协作怎么实现的：同进程编排（生产） vs Inngest 事件链（并存未启用）

① 当前生产 UI 启动 mission 走 executeMissionDirect——server action 内 fire-and-forget，同一 Node 进程顺序 await leaderPlanDirect → executeReadyTasksDirect → leaderConsolidateDirect，任务依赖在进程内循环推进，不经消息队列（dev 不起 Inngest 也能跑全链路）。所以「多智能体协作」当前不是靠 Inngest，而是同进程顺序编排。
② Inngest 5 函数事件链（src/inngest/functions/）是并存的等价实现、事件驱动：mission/created → leaderPlan 发 task-ready → executeMissionTask 发 task-completed → checkTaskDependencies 解阻塞回 task-ready（闭环推 DAG），全完发 all-tasks-done → leaderConsolidate；失败 task-failed → handleTaskFailure 重试/级联。当前 UI 不发 mission/created，故这套未被触发——为未来跨进程横向扩展、重试限流预留。

① 单体自主 Loop

一个 Agent 自己把任务做完

executeAgent 以 generateText({ stopWhen: stepCountIs(20) }) 跑多步循环：LLM 自主规划 → 调用工具 → 观察结果 → 反思 → 继续，最多 20 步、3 分钟超时。onStepFinish 逐步收集工具产物与 success:false 失败，不信 LLM 口头叙述、只认真实工具返回。

② 多智能体协作

一个团队按工种分工协作

leaderPlanDirect（总编 producer 拆解派单）→ executeReadyTasksDirect（各工种 Agent 执行、{{stepN.field}} 传递产物、依赖解除后转 ready 继续）→ leaderConsolidateDirect（汇总终审）。全程同进程顺序 await。

◆ 对标业界领先 Agentic 系统

这两层正对应当前最强 Agent 产品的核心能力：单体强自主执行闭环（如 Claude Code / Devin / Manus——自己规划-调用-反思直到完成，而非一问一答）＋ 团队级多智能体编排（总编派单、多工种并行、产物互传、汇总终审）。VibeTide 的 Mission 引擎把二者合一——既有单兵的执行深度，也有团队的协同广度。

12 · 执行模型

执行模型：两条轴——谁驱动 Agent（入口）· Agent 调什么（工具）

把 Agent 执行模型拆成两条正交的轴讲清，避免混淆：① 驱动轴——谁启动 Agent（Web / Inngest / 定时 / Agent CLI）；② 工具轴——Agent 能调什么能力（同进程 tool() / MCP / 本地命令封装）。SKILL 则是「怎么指导 Agent 干活」（prompt 注入，不在任一轴上）。「CLI」一词有两义——既能指驱动轴的 Agent 入口，也能指工具轴的命令行工具封装，这正是之前讲糊涂的根源，下图与说明会点破。

绿：现状（已实现） 橙虚线：驱动轴待改造（Agent CLI） 蓝虚线：工具轴目标态（MCP · CLI 工具封装）

两条正交的轴：左 = 驱动轴（谁启动 Agent）、右 = 工具轴（Agent 能调什么）。中间 Agent 核心两侧都可插拔——换入口不动核心，加工具来源也不动核心。

ℹ「CLI」有两个意思，别混了——这正是之前图最容易乱的地方

① 驱动轴的 Agent CLI ＝ 把整个 agent 做成命令行程序，人在终端敲命令来驱动 agent 跑（像 Claude Code 那样 vibetide run-skill ...）。它和 Web / Inngest 并列，回答「谁启动 agent」。本章下文 ④「CLI 改造」、spec §8 说的都是这个。
② 工具轴的 CLI 工具封装 ＝ 把某个命令行工具 / 桌面应用（ffmpeg、git、本地脚本）包装成 LLM 能调用的 tool，让 agent 在执行时调它。它和 MCP 同类（都在工具轴、都回答「agent 调什么」）——这才是你说的「工具 / 桌面应用转成大模型能调的命令」。
结论：CLI 不是和 MCP 对立的输入 / 输出，它俩根本在不同的轴——Agent CLI 在驱动轴，CLI 工具封装在工具轴（与 MCP 并列）。

Web 应用的执行边界：前端、后端、用户本地三个域

「Web 应用」不是一个整体，它分前端、后端两半，能力天差地别。讲清这条边界，就知道「调本地命令 / CLI 工具封装 / MCP」各自能在哪一侧落地。下图是三个「执行域」各自能做什么。

三个「执行域」能力边界：浏览器前端沙箱禁本地；服务器后端（Agent 在此跑）可调服务器本地命令；用户本地机器后端碰不到，需本地 agent。

  • 浏览器前端（React）：跑在浏览器安全沙箱里，绝对不能执行本地命令、读写文件、调本地工具（否则任何网页都能控制你电脑）。它只能渲染 UI、发 HTTP 请求。
  • 服务器后端（Node 进程）：VibeTide 是 Next.js 全栈，后端是普通 Node 进程（自托管 Docker，output: "standalone"）。它完全可以 child_process.spawn 调服务器本地的 CLI / 二进制（ffmpeg、whisper、python…）、读写文件、跑原生库——项目已在用 canvas / chartjs-node-canvas（需系统级图形库）就是后端能跑本地原生代码的活证据。
  • 当前现状：所有工具（web_search / cms_publish…）当前都调外部 HTTP API，没有调本地命令——但这是实现选择，不是能力限制。要加个调本地 ffmpeg 的工具，在 tool-registry.ts 写 execute: () => spawn("ffmpeg", […]) 即可，架构开箱支持。
⚠ 关键区分：「本地」是谁的本地？

Web 后端调的本地命令 = 服务器的本地（Docker 容器里装的 ffmpeg 等），不是用户浏览器所在电脑的本地——那台机器后端碰不到（沙箱挡着）、也不该碰。若要像 Claude Code 那样操作用户自己电脑的本地文件与工具，Web 形态做不到，必须把 agent 打包成本地 CLI / 桌面应用（即下文 ④ 的 CLI 改造延伸），让 agent 直接跑在用户机器上。

三种「调本地工具」形态对照

形态调谁的本地机制可行性
Web 后端 child_process服务器本地（容器内）工具 execute 里 spawn 本地命令✅ 架构支持，加工具即可
Web 后端 ＋ 本地 MCP server服务器本地（标准化）后端做 MCP client 连本地 MCP server🔵 需接 MCP（目标态）
本地 CLI / 桌面 agent用户自己电脑agent 装在用户机器跑，直连或经本地 MCP🔵 需 CLI 改造（见 ④）

MCP 的一大典型用途，正是安全、标准地桥接「本地工具」：在本地起一个 MCP server（stdio）把本地命令 / 文件 / 数据库包装成 MCP tools，agent（无论 Web 后端还是 CLI）作为 client 连接它——比裸 child_process 散落各处更可控、可审计。这也是文档多处把 MCP 列为「目标演进态」的原因之一。

那工具到底该部署在哪？

直接回答这个疑问：绝大多数工具就该在服务端（也是当前架构）。只有两类例外需要拆出去——判断只看「这个工具碰不碰特殊系统依赖或用户本地资源」：

工具类型部署位置为什么
检索 / 生成 / 发布（调外部 API、纯计算）——当前全部工具服务端主进程多租户共享、密钥不下发前端、统一鉴权 / 配额 / 审计、可水平扩缩容。默认就该这样
重型 / 特殊系统依赖（ffmpeg 转码、whisper ASR、本地模型推理）服务端 · 独立工具服务 / MCP server单独容器装系统依赖、独立扩缩容、不拖垮主 web 进程（一次转码几分钟会堵请求）
操作用户本地文件 / 工具（读本地素材、调本地软件）用户本地 · 本地 agent ＋ 本地 MCP服务端碰不到用户本地（沙箱）；数据不出本地更安全合规
◆ 部署原则：三档按需升级

默认服务端（一体打包、最简单）→ 工具变重 / 有特殊依赖就拆成独立工具服务或 MCP server（与 web 进程解耦）→ 只有要碰用户本地资源时，才下沉到用户本地 agent。不必一步到位：当前阶段全部工具留在服务端主进程即可，等真有视频转码 / ASR 这类重活，再把那几个工具单独拆成 MCP server。

① SKILL 如何执行：prompt 注入，不是跑脚本

  • 本质：技能是注入 system prompt 的能力指导，不是可执行代码。装配期 assembleAgent 把 SKILL.md 正文读进「技能执行指南层」（assembly.ts:29 / prompt-templates.ts）。
  • 两种来源：builtin 读 skills/<slug>/SKILL.md body；custom / plugin 读 DB skills.content。
  • 执行 = LLM 自主调工具：步骤绑定技能时，skillSpec 整段 pin 进 system prompt，强制三段式输出（execution.ts:190 附近）。LLM 按 SKILL.md 流程自己决定调哪些工具、产出【执行摘要 / 执行过程 / 产出结果】。
  • 子模板 / scriptPath 当前是 stub：src/lib/agent/skills/{duanju,zhongcao,podcast}-subtemplates.ts 均为 export const SUBTEMPLATES = {}，全库无任何代码 import 执行——没有确定性脚本，技能 100% 走 LLM-in-the-loop。

◆ 工具轴 = 同一个「Agent 调什么」的三种来源（呼应上方双轴图右轴）

「Agent 能调什么」有三种工具来源，对 executeAgent 完全等价（都产出一个 ToolSet 喂 generateText），区别只在工具从哪来、跑在哪个进程：① 同进程 tool()（现状：execute 是 JS 函数，随 app 打包）· ② MCP server（跨进程标准协议，可独立部署 / 跨语言）· ③ 本地命令封装（把 ffmpeg / git 等命令行工具用 child_process 包成一个 tool）。后两者是目标态。三者都在工具轴——和「驱动轴的 Agent CLI」不是一回事，别再把 CLI 与 MCP 当成对立的两极。

  target?: { catalogId?; appId?; siteId? };       // 缺省回退 env: site 81 / app 1768 / catalog 10210
}

发布 9 步：flag 检查 → 加载 article+org → 状态校验（approved/publishing/published）→ 加载 MapperContext → 幂等检查 → 映射 DTO → 落 cms_publications(submitting) → 调 saveArticle → 更新 submitted + 触发轮询。

状态机 6 态：submitting → submitted → synced / retrying / rejected_by_cms / failed（终态 synced/failed/rejected）。CMS status 映射："0"/"20"→submitted、"30"→synced、"60"→rejected_by_cms。

ℹ 配置与灰度

必填 env：CMS_HOST / CMS_LOGIN_CMC_ID / CMS_LOGIN_CMC_TID / CMS_TENANT_ID / CMS_USERNAME。Flag：VIBETIDE_CMS_PUBLISH_ENABLED（默认 false 逐 org 灰度）、VIBETIDE_CATALOG_SYNC_ENABLED（默认 true）。配置 UI 在 /settings/cms-mapping。

17 · 设计系统

设计系统约束与 ESLint

每一轮样式漂移都源于绕过共享原语。这套规则（含 ESLint 强制）让 UI 长期不走样。

必须用共享原语，禁止手搓

按钮→<Button>、输入→<Input>、搜索→<SearchInput>、下拉→<Select>、多行→<Textarea>、日期→<DatePicker>、Tabs→用 variant、表格→<DataTable>、标题→<PageHeader>、卡片→<GlassCard>。

  • 禁止在共享组件上用 className 覆盖颜色类（破坏 liquid-glass 风格），改用 variant。
  • 弹层内可滚动列表必须用固定高度 h-X 而非 max-h-X（避免搜索 / 切 tab / 增删时高度抖动）。
  • 项目特别约定：所有可点击触发事件的按钮 / 标签一律不带边框。
